# JDK Flight Recorder (JFR) Guide

## Introduction

Java Flight Recorder (JFR) is a built-in, low-overhead diagnostics and profiling framework available in the JDK. It continuously records JVM events that help developers analyze application performance, identify bottlenecks, and troubleshoot production issues.

Unlike traditional profilers, JFR is designed for production environments and typically introduces minimal runtime overhead.

This project uses the **JFR Consumer API** (`jdk.jfr.consumer`) to read and analyze JFR recordings programmatically.

---

# What is a JFR Recording?

A JFR recording (`.jfr`) is a binary file that contains timestamped events generated by the JVM during application execution.

Each event captures information about a specific activity, such as:

* CPU sampling
* Garbage Collection
* Thread execution
* Monitor contention
* Object allocation
* File I/O
* Socket I/O
* Class loading
* Exceptions

Instead of manually opening these recordings in JDK Mission Control, this project reads and analyzes them directly using Java.

# Generating a JFR Recording

## Step 1 – Find the Java Process ID

```bash
jps -l
```

Example output

```text
12548 com.pratyush.jfranalyzer.JfrAiPerformanceAnalyzerApplication
```

---

## Step 2 – Start Recording

```bash
jcmd <PID> JFR.start name=Performance settings=profile
```

Example

```bash
jcmd 12548 JFR.start name=Performance settings=profile
```

---

## Step 3 – Generate Application Load

Invoke one or more workload endpoints.

```text
GET /cpu

GET /memory

GET /threads

GET /io
```

Each endpoint creates a different JVM behavior.

---

## Step 4 – Stop Recording

```bash
jcmd <PID> JFR.stop name=Performance filename=recordings/demo.jfr
```

The recording is saved in the `recordings` directory.

# Important JFR Events Used in this Project

## CPU Events

### jdk.ExecutionSample

Represents sampled stack traces while the JVM is executing.

Purpose

* Identify CPU hotspots
* Discover frequently executed methods
* Estimate execution distribution

Used in

```text
CpuSummary
```

---

### jdk.CPULoad

Provides JVM and machine CPU utilization.

Metrics extracted

* JVM CPU load
* Machine CPU load

---

# Memory Events

## jdk.ObjectAllocationSample

Represents sampled object allocations.

Purpose

* Detect allocation-heavy code
* Estimate allocation pressure
* Analyze memory behavior

---

## jdk.GarbageCollection

Generated whenever the JVM performs garbage collection.

Metrics extracted

* GC count
* GC frequency

---

# Thread Events

## jdk.ThreadPark

Indicates that a thread is parked or waiting.

Useful for

* Thread waiting analysis
* Synchronization investigation

---

## jdk.JavaMonitorEnter

Generated when a thread enters a synchronized monitor.

Useful for

* Lock contention analysis
* Synchronization bottlenecks

---

# File I/O Events

## jdk.FileRead

Generated when the JVM performs file read operations.

Used to identify

* Heavy disk reads
* File system bottlenecks

---

## jdk.FileWrite

Generated when the JVM writes data to the file system.

Useful for

* Write-intensive applications
* Disk activity analysis

# Parsing JFR Programmatically

The project uses the built-in JFR Consumer API.

Example

```java
try (RecordingFile recording =
         new RecordingFile(Path.of(file))) {

    while (recording.hasMoreEvents()) {

        RecordedEvent event =
                recording.readEvent();

        extractor.processEvent(event, summary);

    }

}
```

Each event is processed immediately, avoiding unnecessary memory usage.

# Why Not Use JDK Mission Control?

JDK Mission Control is an excellent visualization tool, but it requires manual inspection.

This project focuses on automation by:

* Reading JFR recordings programmatically
* Extracting performance metrics
* Applying deterministic performance rules
* Generating AI-assisted analysis
* Producing a PDF report

This approach enables repeatable and automated performance diagnostics.

---

# JFR Best Practices

* Record only the time period you want to analyze.
* Use the `profile` settings for performance investigations.
* Generate representative workloads before stopping the recording.
* Avoid extremely long recordings unless necessary.
* Store recordings for historical comparison.
